# Skill Git Dev

Полный цикл разработки скиллов, отслеживаемых в Git.
Триггер: Паша говорит «сделай/поправь скилл `<имя>`: `<что изменить>`» (в OpenClaw это была команда `/skill_git_dev`).

## Что нужно

- Git-репа склонирована в `~/work/SkillsAndPrompts`
- Рабочая ветка — **`hermes`** (в `master` лежат версии под OpenClaw, их не трогаем)
- Пуш идёт по SSH deploy key этого репозитория (write access включён), remote `origin` — `git@github.com:PavelRubis/SkillsAndPrompts.git`
- Приватный ключ лежит вне репозитория: `~/.hermes/state/id_github_deploy`, подставляется через `GIT_SSH_COMMAND` (см. шаг 8). Токены и ключи в репозитории не хранятся и в ответах не печатаются.

- Автор коммитов в репе:

```bash
git -C ~/work/SkillsAndPrompts config user.name "Hermes Agent"
git -C ~/work/SkillsAndPrompts config user.email "hermes@nousresearch.local"
```

## Порядок действий

### Шаг 1: Подготовить директорию разработки

```bash
mkdir -p ~/.hermes/cache/scratch/skill-dev/<имя>
```

Если скилл существует — скопировать его файлы из `~/work/SkillsAndPrompts/skills/<имя>/` в `~/.hermes/cache/scratch/skill-dev/<имя>/` (`SKILL.md` всегда, плюс `references/`, `scripts/`, `assets/` если есть). Старые файлы в директории разработки удалить — они могли остаться с прошлой сессии.

`~/.hermes/cache/scratch` чистится сам через 24 часа, поэтому это безопасная песочница.

### Шаг 2: Внести изменения

Правки в `~/.hermes/cache/scratch/skill-dev/<имя>/SKILL.md` и support-файлах.

### Шаг 3: Синхронизировать в репу

```bash
cp -r ~/.hermes/cache/scratch/skill-dev/<имя>/. ~/work/SkillsAndPrompts/skills/<имя>/
```

При добавлении **нового** скилла:

1. Прочитать `~/work/SkillsAndPrompts/Readme.md`
2. Взять `description` из frontmatter нового скилла
3. Добавить строку в таблицу скиллов, сохраняя алфавитный порядок:

```markdown
| `имя-скилла` | Описание из frontmatter SKILL.md |
```

4. Добавить `├── skill-name/` в блок дерева директорий

Если скилл удаляется — убрать его строку из таблицы и из дерева.

### Шаг 4: Показать изменения Паше

Ответить: «Скилл `<имя>` готов к коммиту. Вот изменения:» и приложить `git diff` из `~/work/SkillsAndPrompts` по всем изменённым/созданным файлам.

### Шаг 5: Подтвердить аппрув Паши

Дождаться явного одобрения. Не одобрил — вернуться к шагу 2 и пройти цикл заново.

### Шаг 6: Stage и коммит

```bash
cd ~/work/SkillsAndPrompts
git add skills/<имя>/
# если Readme.md обновлялся:
git add Readme.md
git commit -m "<описание на английском>"
```

### Шаг 7: Установить скилл в Hermes

Скиллы Hermes живут в `~/.hermes/skills/<категория>/<имя>/` и управляются тулом `skill_manage` (в OpenClaw это был `skill_workshop` — в Hermes его нет).

- **Существующий скилл:** `skill_manage(action="patch", name="<имя>", content=<полный SKILL.md из репы>)`
- **Новый скилл:** `skill_manage(action="create", name="<имя>", content=<SKILL.md>, category="<категория>")`
- **Support-файлы:** `skill_manage(action="write_file", name="<имя>", file_path="scripts/foo.py", file_content=...)`

Проверить, что скилл виден: `skill_view(name="<имя>")`.

### Шаг 8: Пуш

```bash
cd ~/work/SkillsAndPrompts
GIT_SSH_COMMAND="ssh -i ~/.hermes/state/id_github_deploy -o IdentitiesOnly=yes" git push origin hermes
```

Авторизация — только SSH-ключом; пароли и токены не запрашиваются и не печатаются.

### Шаг 9: Ответ

«Коммит `<хеш>`: `<сообщение>`» + подтверждение, что скилл установлен в Hermes.

## Правила коммит-сообщений

- На английском
- Короткий imperative-формат, заголовок до 72 символов
- Описывать ЧТО изменилось: `add retry logic to yandex-reviews-analyzer`, `update notion-task-create frontmatter`

## Грабли при правке файлов и установке

- **`write_file` отказывает на «stale/partial view»**, если файл читали пагинацией или частичным `limit` — перезапись не пройдёт. Не повторять вызов: либо `rm` файла и записать заново, либо (предпочтительно) править точечным `patch`. Полная перезапись большого SKILL.md почти никогда не нужна.
- **Ставить скилл из репы дешевле копированием**, чем ретайпом полного текста через `skill_manage ... content`: `cp -r ~/work/SkillsAndPrompts/skills/<имя>/. ~/.hermes/skills/<категория>/<имя>/`. Это тот же результат байт-в-байт с репой, без риска опечаток при переносе текста.
- **После установки проверить три вещи:** `diff -r` репа vs установленный каталог (пусто), frontmatter парсится (name/description на месте), `skills_list(category=…)` показывает навык. Категорию выбирать по смыслу: заметки → `note-taking`, задачи/продуктивность → `productivity`, анализ → `research`, медиа → `media`, разработка → `software-development`.
- **`description` во frontmatter виден в индексе навыков.** Штатные скиллы держат 49–60 символов; длиннее — работает, но раздувает индекс, поэтому новое описание сразу писать коротким.
- **Установка — только по явной команде Паши.** Адаптация скилла в репе или в скретч-каталоге не даёт права класть его в `~/.hermes/skills/`: показать дифф и ждать «ставь».

## Как тестировать установленные скиллы

- **Гонять кейсы скилла его же путями.** Сначала `skill_view(name)`, потом выполнять шаги реальными инструментами (API через curl, `node`-скрипт сборщика, `cronjob_manage(action="run")`). Отдельный скрипт «сбоку» проверяет не скилл, а свою копию логики.
- **Верить только чтением назад.** Создал страницу — прочитай `GET /v1/blocks/<id>/children` и `GET /v1/pages/<id>`; запустил cron — проверь `last_status` и сам эффект. HTTP 200 сам по себе ничего не доказывает.
- **Проверки, которые пишут в чужие системы, оставляют мусор.** У Notion-токена удаление не подтверждено, поэтому тестовые страницы называть с префиксом `ТЕСТ …` и в отчёте выдавать Паше список ссылок на удаление — иначе они останутся навсегда.
- **Не портить рабочие state-файлы** (буфер дневника, `diary.json`): перед прогоном сделать копию и восстановить после; кейсы «файла нет / битый JSON» гонять с подменённым `HOME`.
- **Зависимости проверять дешёвыми пробами:** сверка значений select с живой схемой API, наличие моделей в каталоге провайдера, MCP — stdio-проба (`initialize` → `tools/list` → `tools/call`), не поднимая весь рантайм.
- **cron-кейс:** `cronjob_manage(action="run")` уходит в фон, результат придёт отдельным сообщением — не поллить, а проверять эффект напрямую по данным.
- **Отчёт тестирования — по скиллам и кейсам с PASS/FAIL**, включая непройденные кейсы и найденные расхождения между текстом скилла и реальным API.

## Автосинк в репо (каждый день 23:30 МСК)

- Cron-джоба «Skill sync to SkillsAndPrompts» (`skill-git-daily-sync.py` в `~/.hermes/scripts/`) сама: `fetch`+`ff-merge origin/hermes`, сравнивает каждый скилл репы с локальной копией, копирует локальные правки в репо, коммитит по одному коммиту на скилл (`sync <имя>: <файлы>`) и пушит; Паше уходит отчёт, при отсутствии изменений — молчит.
- Направление — локальная копия → репо. Репо → локальная копия только если pull принёс изменения, а локальная копия не тронута; если тронуты обе стороны — скилл пропускается как конфликт и ждёт решения Паши.
- Поэтому ручной цикл «дифф → аппрув → коммит» нужен только когда правка спорная или Паша просит показать дифф заранее. Авторевью скиллов в аппруве не нуждается (разрешено Пашей 20.11.2026): правки локальной копии можно спокойно оставить до ночного синка.

## Заметки

- Авторизация — только SSH deploy key, привязанный к этому репозиторию. Никакие токены в репо и в ответах не появляются.
- Ветка `hermes` — единственная, куда пушит агент. Merge в `master` — решение Паши.
